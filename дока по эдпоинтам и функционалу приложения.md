# Дока по эндпоинтам и функционалу приложения

Статус: черновик контракта. Документ описывает текущий фронтенд и целевой backend-контракт. По мере замены моков на реальный API статусы и детали обновляются здесь.

## 1. Приложение

Angular-мессенджер. Основные возможности:

- вход, регистрация, восстановление сессии, выход;
- настройки аккаунта: имя, тэг, смена пароля;
- список чатов, личные и групповые чаты;
- поиск по чатам и пользователям, поиск по `@тэгу`;
- сообщения: отправка, ответы, редактирование, удаление, пересылка;
- вложения: изображения и файлы;
- поиск по сообщениям: сначала по загруженным, затем по всей истории;
- пагинация истории в обе стороны;
- черновики по чатам;
- непрочитанные и превью последнего сообщения;
- мобильная раскладка: список чатов и чат на весь экран, кнопка назад.

Осознанно не реализовано:

- прочитанность сообщений;
- online/typing;
- deep links/routing для чатов;
- мобильное приложение beyond responsive web.

## 2. Общие правила API

- База: `/api`.
- Авторизация: `Authorization: Bearer <token>`. Токен добавляется `authTokenInterceptor`; в mock-режиме запросы обрабатывает `authMockInterceptor`.
- ID сущностей — строки цифр, генерирует сервер.
- Даты — ISO 8601 с часовым поясом.
- Ответы с ошибкой:

```json
{
  "statusCode": 400,
  "message": "Человекочитаемое сообщение",
  "error": "Bad Request"
}
```

- Список сообщений — курсорная пагинация, без offset.
- Сервер владеет: ID, `createdAt`, `editedAt`, превью чата, снимком реплая, `forwardedFrom`, URL вложений.
- Клиент не должен сам придумывать ID или собирать `lastMessage` для чата.

## 3. Модели

### User

```json
{
  "id": "1",
  "username": "anya_sokolova",
  "displayName": "Аня Соколова",
  "avatarUrl": null
}
```

### ChatListItem

```json
{
  "id": "2",
  "title": "Фронтенд-команда",
  "lastMessage": "Созвон в 19:00",
  "lastMessageAt": "2026-10-19T17:05:00+06:00",
  "lastMessageAuthorId": "2",
  "lastMessageAuthorName": "Аня Соколова",
  "unreadCount": 0,
  "peerUserId": null,
  "ownerId": "2"
}
```

Для личного чата `peerUserId` заполнен, `ownerId` отсутствует. Для группы `peerUserId: null`.

### MessageAttachment

```json
{
  "id": "1001",
  "name": "screen.png",
  "type": "image/png",
  "size": 34821,
  "url": "https://cdn.example.com/attachments/1001",
  "isImage": true
}
```

### Message

```json
{
  "id": "2008",
  "chatId": "2",
  "authorId": "3",
  "text": "Поиск почти готов",
  "createdAt": "2026-10-19T09:20:00+06:00",
  "editedAt": null,
  "replyToId": "2005",
  "replyTo": {
    "messageId": "2005",
    "authorId": "2",
    "authorName": "Аня Соколова",
    "text": "Проверь пустое состояние"
  },
  "forwardedFrom": null,
  "attachments": []
}
```

`replyTo` — снимок на момент отправки. Если оригинал удалён, снимок всё равно позволяет показать цитату.

`forwardedFrom`:

```json
{
  "authorId": "3",
  "authorName": "Максим Иванов"
}
```

### MessagePage

```json
{
  "messages": [],
  "hasMoreBefore": true,
  "nextBefore": "2001",
  "hasMoreAfter": false,
  "nextAfter": "2020"
}
```

- `nextBefore` — ID первого сообщения страницы; передаётся как `before`.
- `nextAfter` — ID последнего сообщения страницы; передаётся как `after`.
- Для начальной страницы `hasMoreAfter: false`.

## 4. Эндпоинты

### Auth

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/register` | Регистрация |
| POST | `/auth/login` | Вход |
| GET | `/auth/me` | Текущий пользователь по токену |
| PATCH | `/auth/profile` | Имя и тэг |
| POST | `/auth/change-password` | Смена пароля |
| POST | `/auth/logout` | Выход |

Регистрация:

```json
{ "login": "user 3", "password": "secret" }
```

Ответ:

```json
{
  "token": "jwt-token",
  "user": {
    "id": "1000",
    "username": "user_3",
    "displayName": "user 3",
    "avatarUrl": null
  }
}
```

Правило тэга: пробелы заменяются на `_`, разрешены буквы, цифры, `_` и `-`, остальные символы удаляются.

### Chats

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/chats` | Список чатов пользователя |
| POST | `/chats/direct` | Создать/получить личный чат |
| POST | `/chats/groups` | Создать группу |
| PATCH | `/chats/:chatId` | Переименовать группу |
| DELETE | `/chats/:chatId` | Удалить группу |
| GET | `/chats/:chatId/members` | Участники группы |
| POST | `/chats/:chatId/members` | Добавить участников |
| DELETE | `/chats/:chatId/members/:userId` | Удалить участника |

Создание личного чата:

```json
{ "userId": "2" }
```

Создание группы:

```json
{
  "title": "Новая группа",
  "memberIds": ["2", "3"]
}
```

Сервер сам добавляет создателя владельцем и возвращает готовый `ChatListItem`.

### Messages

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/chats/:chatId/messages?before=&after=&limit=` | История |
| GET | `/chats/:chatId/messages/context?messageId=&radius=` | Контекст вокруг сообщения |
| GET | `/chats/:chatId/messages/search?q=` | Поиск по всей истории |
| POST | `/chats/:chatId/messages` | Отправить сообщение |
| PATCH | `/messages/:messageId` | Редактировать текст |
| DELETE | `/messages/:messageId` | Удалить сообщение |
| POST | `/messages/:messageId/forward` | Переслать |

Отправка:

```json
{
  "text": "Ответ",
  "replyToId": "2005",
  "attachmentIds": ["1001"]
}
```

Сервер возвращает готовый `Message`, включая `replyTo` и вложения.

Пересылка:

```json
{ "targetChatId": "4" }
```

Ответ — новое сообщение в целевом чате с `forwardedFrom`.

Пагинация:

- `before` — загрузить сообщения до указанного ID;
- `after` — загрузить сообщения после указанного ID;
- `limit` — размер страницы, по умолчанию 20;
- `context` — вернуть `radius` сообщений до и после target.

### Attachments

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/attachments` | Multipart upload, вернуть `MessageAttachment` |
| GET | `/attachments/:id` | Скачать/открыть файл |

Клиент загружает файлы заранее, получает ID и передаёт их в `POST /messages`.

### Users

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/users` | Справочник пользователей |
| GET | `/users/:id` | Профиль пользователя |
| GET | `/users/search?q=&tagOnly=` | Поиск пользователей по имени или `@тэгу` |

### Realtime / notifications

Планируется отдельным этапом: WebSocket или SSE для входящих сообщений, unread и уведомлений. Контракт пока не зафиксирован.

## 5. Поиск

### Чаты и пользователи

- Запрос начинается с `@` — ищем только пользователей по `username`.
- Иначе — локальные чаты + API-поиск пользователей.
- Текущий пользователь исключается.

### Сообщения

1. Поиск по уже загруженным сообщениям текущего чата.
2. Если локально ничего нет и запрос ≥ 2 символов — `GET /messages/search`.
3. Клик по результату загружает контекст вокруг сообщения и подсвечивает его.

## 6. Текущая реализация и что заменить

| Слой | Сейчас | Цель |
|---|---|---|
| Auth | `AuthMockInterceptor` + JSON-аккаунты | Реальный `/auth`, JWT, refresh |
| Chats | JSON `assets/mocks/chat-list/*` | `GET /chats`, мутации на сервере |
| Messages | JSON + локальный кеш мутаций | REST-мутации и серверные страницы |
| Groups | `GroupInfoApiService` в памяти | `/chats/:id/members` |
| Attachments | object URL | upload + постоянные URL |
| Users | JSON `users.json` + `search-users.json` | `/users/search` и справочник |
| IDs | `MockIdService` | серверные ID |
| Уведомления | сервис без источника | WebSocket/SSE |

## 8. Состояние адаптации

Сделано:

- введены абстракции `AuthApi`, `ChatsApi`, `MessagesApi`, `GroupInfoApi`, `AttachmentsApi`, `UserDirectoryApi`;
- компоненты и сторы зависят от абстракций, а не от мок-классов;
- добавлены HTTP-реализации в `core/api/http/`:
  - `HttpChatsApiService`;
  - `HttpMessagesApiService`;
  - `HttpGroupInfoApiService`;
  - `HttpAttachmentsApiService`;
  - `HttpUserDirectoryApiService`;
- mock/HTTP переключаются флагом в `core/api/api-config.ts`:

```ts
export const API_SETTINGS: ApiConfig = {
  baseUrl: '/api',
  useMockApi: true,
};
```

При `useMockApi: false` отключается `authMockInterceptor`, а все запросы идут на `API_SETTINGS.baseUrl`. `authTokenInterceptor` добавляет Bearer-токен в оба режима.

Mock-реализации остаются реализациями тех же контрактов. HTTP-адаптеры покрыты contract-тестами (`http-api.spec.ts`). Приложение по умолчанию продолжает работать на mock; HTTP-режим включается флагом.

Для backend-разработчика:

1. Реализовать endpoint’ы из раздела 4.
2. Установить `API_SETTINGS.useMockApi = false`.
3. Указать `API_SETTINGS.baseUrl`, если API не на `/api`.
4. Проверить коды ошибок и форматы `MessagePage`.
5. Заменить мок-ассеты не требуется — при HTTP-режиме они не используются.

Следующие шаги:

1. Contract-тесты HTTP-адаптеров — базовые уже есть, расширять по мере backend-ответов.
2. Реальный upload вложений и отображение прогресса.
3. Realtime-канал и уведомления.
4. Убрать `MockIdService` из production-сборки окончательно.
5. Проверить HTTP-режим против реального сервера.

## 9. Критические сценарии для проверки

- вход и восстановление сессии;
- список чатов и непрочитанные;
- открытие личного и группового чата;
- создание группы и загрузка участников;
- отправка, ответ, редактирование, удаление;
- пересылка в другой чат;
- поиск сообщения и переход к контексту;
- вложения: изображение и файл;
- reload без потери серверных данных.
